# 2026-09-01 每日提醒与自然语言路由整改审核

## 问题结论

- `partner` 截图中的消息是文字输入，不经过本地语音识别。失败主因不是 ASR，而是时间解析器只接受 `8:30` / `8点30分`，没有把时间语境中的 `8.30` 识别为钟点；严格路由因此失配并触发一次完整自动分类，最终又被写入保护层拒绝。
- 即使改写为 `8:30`，旧实现仍把每天、多时段和无总次数重复统一视为不支持。这是功能限制，不是用户意图不明确。
- 原保护层把“本地规则没有命中”近似等同于“用户没有授权”，导致模型已正确理解时仍返回通用拒绝。安全边界保留，但不再要求用户套固定句式。

## 实施方案

- 明确文字提醒继续走本地零 Token 路径。时间语境中的 `8.30` 可解析为 `08:30`，同时通过上下文约束排除 `2026.09.01`、`1.50升`等日期和数值。
- 文字消息支持每天 1—8 个明确且不重复的钟点，例如“每天早上8.30，晚上7点提醒我喝中药”。每天规则只创建一个滴答任务；微信本地队列为各钟点保存一条当前待发记录，送达后原子生成该钟点下一次未来记录，避免一次性预生成无限数据。
- 发送前明确失败仍按原退避策略重试；发送结果不确定时当前记录不重试，避免重复投递，同时滚动保留下一次每日提醒。进程中断造成的陈旧发送状态采用相同处理。
- 取消“本次”会跳过最早一次并继续该钟点的后续链；取消“整个系列”或完成任务会先关闭所有每日链，已进入微信发送调用的当前消息不承诺撤回。
- 本地严格路由未覆盖、但存在未引用、未否定、直接面向秘书的“提醒我”表达时，允许一次任务专用模型辅助理解。模型不能直接决定写入：事项、日期、钟点、重复字段仍从原话重新提取和核对。转发、引用、第三方陈述、状态追问、功能询问和撤回表达不进入此兜底。
- 由于真实语音中曾出现“明天/每天”混淆，本轮不放开语音的无限每日创建。语音识别为每天时先显示本机实际转写并要求确认；用户可用文字重发每日规则，或用“不是每天，是明天”等短句纠正为单次提醒。

## Token 边界

- 截图原句及单时段文字每日提醒均由本地完成，理解模型调用数为 0。
- 只有本地语法未覆盖但直接提醒意图可靠的复杂说法才调用一次任务专用结构，避免使用包含任务、笔记和查询的完整自动分类结构。
- 不增加聊天历史、二次模型审核或循环重试；模型输出仍受现有长度上限和本地来源校验约束。
