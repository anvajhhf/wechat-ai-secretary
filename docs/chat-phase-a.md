# 日常聊天与连续对话：阶段 A 实施说明

日期：2026-10-21。全程负责人：主代理 `/root`。范围：完成升级方案 A，保留现有提醒、任务和笔记执行链。状态：开发、离线验收和独立审核已完成；经用户授权，已按 owner → partner 顺序启用两个在线秘书并完成启动核验。未发送微信测试消息、未调用真实模型进行验收。

## 交付内容

- 无明确办事意图的普通输入进入日常聊天；支持有限连续追问、聊天前缀、临时聊天、新话题与清空。
- 复用 Hermes `ctx.llm.complete`，新增独立聊天用途配置，不运行通用代理工具和自动记忆。纯聊天一次生成，不把历史交给任务/笔记分类器。
- 每档案独立 `assistant.sqlite3`，只在平台明确确认发送后保存成对文本；默认 10 轮、总文本预算 12000 字、输入 6000 字、输出 4000 字、保留 7 天。
- 读取/写入/启动清理过期数据，独立线程每小时补清。关闭聊天但库已存在时仍清理。进程停止期间不执行定时清理；维护线程故障降级到按访问/下次启动清理，日志只记错误类型。
- 私密、私密下一条、语音私密先于聊天处理；临时聊天不读旧对话、不保存本轮正文。非私密输入和必要历史会按已有模型配置出站。
- 原图片/音频不入聊天库；处理后的当轮图片可用于聊天，单独发图仍保留原先笔记路径。语音沿用本机转写。
- 聊天失败、聊天存储初始化失败或维护线程失败，不禁用现有明确任务、提醒与笔记功能。聊天表与提醒队列独立。
- 新话题切换会话代际；清空删除当前会话所有旧话题正文。旧代际的迟到回执不能重新写入。

## 分歧、依据与一致处理方案

| 议题 | 实现提案 / 审核意见与依据 | 一致方案及结果 |
|---|---|---|
| 闲聊后是否继续旧任务草稿 | 原测试允许“下午三点是什么意思？”后继续用“下午三点”补旧草稿；聊天场景里这可能把新话题误当作旧任务补充 | 开启聊天时进入普通聊天即结束未执行草稿；关闭聊天保留原行为。新增两种开关测试，旧测试不改预期 |
| 只在聊天开始时失效任务焦点 | 初实现提案只在入口失效；审核指出生成期间提醒线程会重新写入最近任务 | 聊天入口与确认发送后均原子失效焦点；只修改指代元数据和未执行澄清，不删除提醒或完成标记 |
| 提醒发送后延迟记账 | 仅二次失效仍挡不住提醒线程的晚记账 | 新增失效时间屏障；调度通知使用 `reminder-delivery` 来源，早于或等于屏障的通知不能恢复匿名焦点。具名补设仍保留原来源；真正更新的通知可恢复焦点 |
| 焦点更新时间排序 | 审核指出已排队用户请求的接收时间可能比期间提醒的轮询时间早 | 保留旧排序的保守拒绝，不扩大提醒时间语义变更。固定测试确认该交错下匿名完成可能被拒绝，但具名完成正常；不存在完成错误目标的降级 |
| 关闭聊天后的期限清理 | 初实现仅在启用时打开聊天库，关闭后会让旧正文超过保留期 | 只要库已存在仍初始化清理和独立维护，但关闭时不创建聊天生成器、不注入历史；保留清空入口 |
| 清理线程启动失败 | 审核用模拟 `Thread.start` 异常复现：曾落入全局 FailClosedBridge | 将维护启动故障隔离在聊天模块；保留原桥接和提醒调度，降级清理方式明确记录 |
| 发送成功时聊天库读取失败 | 审核用合成任务复现：`get_generation` 抛错会跳过焦点失效，随后“搞定了”可误完成旧任务 | 无法读取代际时停止保存正文，但仍保守失效旧任务指代；明确读到代际不同才跳过旧回执 |
| 焦点库瞬时写失败 | 对发送成功后的焦点更新失败，双方讨论是否扩大持久恢复架构 | 受影响会话记录内存待恢复标记；下一次经过授权和私密分流后先重试失效，仍失败则拒绝该轮操作。其他会话与提醒调度不受影响。本阶段不宣称该额外内存防线能跨进程重启保存 |
| 写作、分析及情绪句误建任务 | 审核用合成数据复现“帮我写一段明天下午三点开会的通知”“帮我分析一下明天提交报告的利弊”“明天开会有点紧张”被旧自然日期动作规则建为任务 | 聊天开启时，在草稿续接之前识别锚定外层的讨论请求和限定的明确情绪陈述，只进入无工具聊天；真实外层提醒与强制待办/笔记不受影响。不宣称覆盖所有自然语言 |
| 文案追问被当成改提醒 | 审核复现“写开场白→改成更简洁一点”被提醒修改解析截走 | 只在已有有效聊天、没有活跃任务和待确认操作时，把明确的风格/语言/长度修改交回聊天；涉及日期、时间、次数的含糊修改仍要求明确对象 |
| 新情绪词抢占明确操作 | 审核实测“完成：整理担心的问题”被情绪词抢为聊天；同理涉及具名取消与查询 | 已有 completion、具名提醒控制、QUERY/NOTE/MIXED 和原链接 NORMAL/DEEP 判据优先；显式“聊天：”仍表示只讨论。固定测试覆盖情绪词位于操作正文 |
| 链接笔记兼容 | 负责人自查发现新增分析/总结词会抢占原来支持的“总结一下 URL”链接笔记 | 双方同意保留旧链接笔记纯函数判据优先，不增加联网；显式聊天/临时聊天含 URL 时仍只聊，不读取网页 |

## 验收方式与结果

开发及离线验收全部使用合成消息、临时数据库、假模型及假发送接口；这些测试未连接真实微信、未创建真实滴答任务。笔记写入测试只使用临时 Vault。后续线上启用与启动核验另见下文。

- 初始已有回归抽查：89 项通过。
- 第一轮全量回归：678 项通过，其中新增聊天存储和集成测试 55 项。
- 补充焦点并发验收：8 项通过，包括提醒实际调度代码配合假发送接口，以及回执记账故障不触发重复发送。
- 最终全量回归：719 项全部通过（含原有 623 项与新增 96 项），5.082 秒；新增测试包括存储/生成器 25 项、会话兼容 44 项、并发焦点 8 项、生命周期/故障 19 项。
- 独立审核者另行运行上述 96 项新增测试全部通过；收尾审核无阻塞项、执行与审核无未达一致事项。
- 异步测试需允许本地事件循环套接字，部分 Windows 路径读取也受沙箱限制；在正常本机权限下完成全部离线测试。没有为绕过环境限制修改产品逻辑。
- `git diff --check` 通过；README 仅有仓库既有换行转换提示，无空白错误。
- 仓库当前文件及可达历史的敏感信息扫描通过，检查未输出文件正文。

## 启用、回退与边界

旧配置没有 `[chat]` 时默认关闭。要启用，在对应档案配置中设置 `[chat] enabled = true`，按已有方式逐个重启档案；不要同时停两个秘书。保留当前微信、滴答授权和模型配置，不改变现有提醒发送算法。

关闭同一开关并重启即可停止聊天生成。聊天库保留期限清理继续，原笔记与提醒保留。新焦点元数据只是防止匿名操作旧对象；使用完整任务名称的操作不依赖该模糊指代。

为保留旧用法，“明天开会”等不带讨论意图的裸时间行动仍按原任务规则处理；只想讨论时可明确使用“聊天：”。含糊的时间修改仍走原提醒安全检查，不能自动推测是在改文案还是改提醒。讨论句又追加办事要求的复杂混合表达，第一步优先只讨论，请另发完整的明确操作指令。

保留期限和清空针对本系统聊天库，不撤回已发送微信消息，不承诺清除操作系统快照或用户自行复制的数据库。现有备份脚本未增加聊天导出。第一步尚未实现长期记忆、笔记检索、自动人物画像或实时联网聊天。
