# 2026-08-30 第二轮整改与交叉审核

> 这是特定历史版本的审核快照。测试数量和部署状态可能已经变化，请以当前代码、CI 和本机状态检查为准。

本轮由主 Agent 实施整合，独立审查覆盖意图与模型边界、任务生命周期、微信入口与隐私，并相互复核。范围覆盖消息进入、语音转写后的文本、路由、澄清草稿、滴答写入与回读、本地提醒、完成任务、私密保存、模型调用范围及安装补丁。不是形式化证明，也不保证无剩余缺陷。

## 截图问题的根因与修复

- “提醒我4点半看一下微信助手，下午4点半”：原解析只读取提醒词附近的时间，漏掉句尾“下午”，还把后缀混进标题。现只提取独立且完全由时间构成的后缀，合并相同时间，冲突时澄清；正文中的会议时间、书名和引用保持为正文。
- “今天”：原来的裸钟点被当成已确定的凌晨时间。现保留“尚未确认上午/下午”的状态，只回复日期不会强行判定时间已过。
- “今天下午4点半，提醒我看一下微信助手”：纯时间前缀的标点白名单与后续解析不一致。现逗号、句号、分号、顿号和换行均有服务级回归。
- 日期省略且时刻明确、今天尚未到点时默认今天；模糊钟点、真实冲突、已过去时间不猜测。缺事项的草稿跨午夜也不会悄悄改日期。

## 审核额外发现并整改的问题

| 链路 | 发现的问题 | 处理 |
|---|---|---|
| 微信消息入口 | 相同“今天”被内容去重丢弃；连续文字合并；慢语音下载被后续文字超越 | 保留消息 ID 去重；项目专用入口禁合批和内容去重，同发送者下载有序、同会话工作队列有序 |
| 私密保护 | 原生引用包装掩盖用户自己的私密前缀；过载丢掉私密开关后可能按普通消息处理正文 | 验证原生包装来源；异常时拒绝处理；失败保护跨重启保留，仅较新的成功重试能解除，后续正文不送模型或 ASR |
| 完成与改期 | 用户级上下文可能跨聊天；旧确认或旧取消影响新任务状态 | 会话级上下文，确认列表兼容迁移，成功控制后推进时间边界，旧请求不得覆盖新状态 |
| 逾期提醒 | 合并仅显示前 10 项却把后续项也标记已发送 | 每 10 项独立发送与记账，失败组独立处理 |

| 任务元数据 | 正文/引用/否定中出现分类名也可能被套为分类 | 分类需明确命令或独立简写；否定和冲突不授权归类 |
| 滴答回读 | 只核对标题与清单，截止时间或优先级写错仍可能报成功 | 用既有一次回读核验请求字段，缺失或矛盾标记结果不确定，不重复创建 |
| 安装一致性 | 只改被忽略的运行副本，重装可能丢修复 | 纳入可追踪补丁和幂等安装流程；缺兼容标记则项目入口拒启动 |

## 验证与成本边界

- 最终全套离线测试 **383 项通过**，比基线新增 74 项：口语时间 10、意图与分类 12、生命周期 21、真实适配器入口 26、写入契约与离线示例 5。Python 编译、全部 PowerShell 脚本语法、仓库凭证扫描、两套档案的合成数据加密备份自检均通过。新增兼容补丁在锁定版本上的正向应用检查和本机已应用版本的逆向检查均通过。
- 新增截图口语、意图、生命周期、真实适配器入口和写入契约测试；使用固定时间、假外部服务和合成数据，不发送真实微信、不修改真实滴答任务、不调用 DeepSeek。
- 对私密、并发、重复消息、乱序确认、过期、跨聊天、发送不确定、回读字段不符等执行正反例验证；入口测试直接运行项目锁定版本的微信适配器代码，不只替换语音转写结果。
- 常见单提醒和补字段为零模型调用；复杂输入仍保留有限模型解析。未增加模型输出上限、会话历史或二次模型审核；底层瞬态重试仍可能影响实际账单。
- 语音模型、语音依赖、权重与配置均未更换；本轮不下载模型。原始语音转写质量仍需使用真实音频单独验收。
- 私密失败保护仅保存发送者哈希和随机状态标记，不保存正文；用临时数据库关闭重开验证了恢复。数据库本身不可写且同时断电不在无损保证范围内。
- 本轮只修改与离线验证代码，不把“文件已修改”称为“线上已经修复”。安装补丁已在本机运行副本离线验证，但已有进程不会热更新；需要后续明确部署并重启两套网关。
- 网关进程存活、微信连接正常不等于意图及端到端写入均正常。升级后应以文字和语音逐项确认“今天下午4点半提醒我…”、“提醒我4点半…，下午4点半”、“今天/下午”的补充对话，以及私密开关后发消息。
- 入口时间戳以收到消息时为准；有序处理能防本机下载与工作线程造成的乱序，不能证明所有微信服务端延迟消息的真实发送顺序。

固定 08:00/22:00 自动汇总保持关闭，不重新创建；用户自己设置的提醒保留。该记录不包含凭证、用户消息日志或真实任务内容。

## 部署时追加发现的 SQLite 保护

首轮修复已于 2026-08-30 推送并切换到两套网关。部署日志暴露出本机链接的 SQLite 3.49.1 仍处于 WAL-reset 缺陷影响范围；Hermes 自己的数据库已回退到 DELETE，但秘书独立状态库此前仍无条件启用 WAL。两套数据库完整性检查正常，未发现损坏。

该缺陷需要同一数据库的多个连接并发写入或检查点操作，日常单连接加锁路径降低了触发机会，但不能据此忽略其他连接或未来部署并发。依据 [SQLite 官方 WAL-reset 说明](https://www.sqlite.org/wal.html#walresetbug)，用户已批准追加最小保护：秘书状态库统一采用 DELETE 回滚日志和 EXTRA 同步，避免依赖版本分支或更换运行库。磁盘库必须核验实际模式为 DELETE；无法切换时关闭连接并拒绝启动，不能隐式回退到 WAL。内存测试库保留 MEMORY 模式。

切换流程保持逐档案进行：先加密备份，暂停该档案的引导与健康任务，停止旧 worker，确认退出后再启动新版。由 SQLite 自己转换日志模式，不删除日志文件，不重建数据库，不修改历史提醒或私密保护状态。语音模型、Python 与媒体依赖均不更新。

追加保护经过独立交叉复核，新增 8 项 SQLite 隔离测试，全套当时为 **391 项通过**。测试覆盖旧 WAL 无损迁移、已提交但尚未写回主库的数据恢复、另一连接持读/写锁时拒绝切换、错误模式/同步级别拒绝启动、初始化失败关闭连接，以及双 DELETE 连接交替写入下的状态一致性；截图与零模型调用回归仍通过。
